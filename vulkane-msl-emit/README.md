# vulkane-msl-emit

The Metal Shading Language compute-kernel emitter for [Unpopped](https://crates.io/crates/unpopped) (ROADMAP row 8o).
`Msl::lower_kernel` lowers a 32-bit integer kernel-layer kernel to MSL through `vulkane-kernel-text`: a `kernel void`
entry with `device` buffers bound by `[[buffer(n)]]`, `threadgroup` arrays, the thread and threadgroup position
builtins, `threadgroup_barrier`, and structured control flow. Anything it cannot spell is a typed `UnsupportedKernel`
naming it; the NVIDIA-only statements of board 434 C are refused by name.

**Subgroup collectives (board 506 A), integer kernels only.** Board 506 A (narrowed; CireSnave 2026-11-26): lifted by CireSnave as his risk call; "outside as read" is a reading of public documents, not a clearance; no attorney; findings, not advice. Lifted: subgroup-scope `Reduce` (Sum, Prod, Max, Min, And, Or, Xor), `Shuffle`, `Vote` and `Broadcast`. Still declined by name with the 434 C marker: `Scan`, `ReduceWith`, `ScanWith`, `CollectiveTuple`, every block-scope collective, and every collective on GLSL and SPIR-V. Lowered to `simd_sum`, `simd_shuffle` and the other SIMD-group functions of MSL 4.1 6.10.2. `Ballot` and every float kernel stay declined. The text is pinned by tests, and the 14 integer cases (7 reductions, All and Any, a constant broadcast, Idx, Up, Down and Xor shuffles) ran on the hosted paravirtual device in run 45970669904 (hosted `macos-latest`, PR #187, 2026-11-27; the same paravirtual device and toolchain as the earlier runs, simd width 32) and matched Unpopped's CPU oracle word for word (14 of 14). That is the paravirtual device only, not Apple hardware; there is no device-side mutant for these cases; floats and `Ballot` are unmeasured and declined.

**Float subgroup reductions (board 506 A float ruling, pm-kernels 2026-11-27): `F32` Sum, Max and Min only.** Lifted by CireSnave 2026-11-26 (board 506 A) as his risk call; "outside as read" is a reading of public documents, not a clearance; no attorney; findings, not advice. Sum lowers to `simd_sum`; Max and Min lower to `simd_max` / `simd_min` wrapped in `select(.., NAN, simd_any(isnan(v)))`, because the bare functions IGNORE a NaN operand (measured) and KISS-OPS-6.11-0002 requires a float reduce(max|min) to propagate it. **Measured on the hosted macOS paravirtual device, not Apple hardware; safe math only; fast-math was not measured: a kernel compiled with fast-math may differ.** The +-0 bits of a float Max or Min are not pinned by KISS and nothing is claimed about them. A float Sum's order is not pinned (KISS-OPS-6.0-0004); the device cases compare it under a tolerance that is OURS, not KISS's (the clauses state no bound). `Prod`, `Mean`, shuffles, votes, broadcasts, scans, half and bfloat stay declined by name (unmeasured or outside the ruling).

**Compiled by Apple's `metal` only in an advisory CI job.** The text is pinned by tests; the hosted macOS job `metal` in
`.github/workflows/metal-probe.yml` also compiles every kernel the emitter lowers in `tests/metal_dump.rs` with `xcrun metal` (not a required
check). It runs no kernel: a hosted runner's Metal device is only probed
and recorded, so Metal numerics stay unmeasured. Treat the output as compile-checked, not run.

**Measured on the paravirtual device, run 45651275958** (hosted `macos-latest`, 2026-11-25; Xcode 26.6, Apple metal 32023.883, macOS 26.7.2; device `Apple Paravirtual device`, simd width 32, `supportsFamily` apple7/apple9/metal3 all false yet it executes compute). Claims are for that paravirtual device only, not physical Apple hardware.

- *Compiled* (`xcrun metal -std=metal3.2 -c`, 27 of 27 kernels, one `metallib` each), including `isnan` on `bfloat`. A threadgroup array sized by a function constant is REJECTED (`array size is not a constant expression`), which is why a scalar parameter is a named blocker.
- *Run, oracle vs device byte for byte* (32 cases in run 45651275958, 42 in run 45748530618 with the Bf16 and subnormal cases added; `tests/metal_device.rs` and `.github/metal/run.swift`; the oracles are the ones the Vulkan device tests use): integer reverse through threadgroup memory with a full barrier, a private array, masked load/store, a 3-D grid, nested loops with break/continue/return, 1024 contended relaxed atomics across 16 threadgroups (exact sum; one CAS winner is not separately asserted), `LaneId`/`SubgroupId`/`SubgroupSize` at simd width 32, F32, F16 and Bf16 multiply-add/max/min/floor (Bf16 through the `bf16_kernel` oracle in `vulkane-test-support`), I8/U8/I16/U16 widen and wrap. Each mutant or control must differ from the oracle and does: the racy atomic, the F16 and Bf16 mutants (fused, flushed, NaN-ignoring), the wrong sign/zero extension.
- *Moved from text-pinned to measured on this device:* the spelled atomics (`atomic_fetch_*_explicit`, relaxed, weak compare-exchange in a retry loop) lose no update at device scope; the subgroup id spellings are right at width 32; the safe-math and `contract(off)` pragmas leave F32/F16 multiply-add unfused and max/min NaN-propagating for the oracle's value pairs; the narrow-buffer spellings and the narrowing cast wrap; masked access skips the memory where the mask is false.
- *Measured on subnormals (run 45748530618):* this device FLUSHES F32 and Bf16 subnormal operands and results to zero (a smallest-subnormal `fma` gives 0 where IEEE gives the subnormal), and PRESERVES F16 ones (the F16 multiply-add pair that reaches a subnormal matches exactly). MSL 8.1 allows the flush, so the subnormal cases accept the exact or the flushed answer and record which; `math_mode(safe)` does not turn it off. A kernel that must see a subnormal needs F16, or must not run on this device.
- *What this means for `Exact` (KISS ops, the bit-stable clause: a kernel that flushes subnormal inputs or results "does not round at the storage dtype's full precision, so it is non-conformant under **bit-stable** and MUST decline `Exact`"):* on the measured device MSL `F32` and `Bf16` output cannot claim `Exact`/bit-stable (they flush), and `F16` can, for the value pairs the oracle tests. The emitter exposes no exactness or fidelity declaration (`Backend` has none, the plan path is not implemented, a `GeneratedKernel` states none), so there is nothing here to switch off: a caller that needs `Exact` declines `F32`/`Bf16` MSL on this evidence. Another device may preserve subnormals; it has to be measured the same way, not read from a capability.
- *Still text-pinned or unmeasured:* *(8q, run 45751664371)* `I64` and `U64` kernels lower (`long`/`ulong`, 6-bit shift counts, a total `Div`: a zero divisor gives the dividend, signed `MIN / -1` gives `MIN`) and run exactly on the device (the shared wide kernel, every result across the 32-bit boundary, matches its oracle at both signednesses and differs from the other signedness' oracle); 64-bit atomics are DECLINED by name: the specification (4.1, 6.16.4.6) permits only `atomic_max_explicit` and `atomic_min_explicit` on `atomic_ulong` (device memory, `memory_order_relaxed`, void result); Apple's compiler rejects the `atomic_fetch_*`, load, store and compare-exchange forms (five flag combinations: `-std=metal3.1/3.2/4.0`, macOS minimum 15.0/26.0), accepts the permitted max/min spelling, and the hosted paravirtual device then FAILS to create a compute pipeline for it (`CompilerError`, "Compilation failed", run 45752252131), so 64-bit atomics are UNMEASURED-ON-HARDWARE (ROADMAP 8r); 32-bit integer `Div` (I32 and U32, every pair of the shared corner values incl. a zero divisor and signed `MIN / -1`) runs exactly and its unguarded-zero-divisor mutant differs (run 45752252131); and `ExecId::DeviceRank`/`DeviceCount` are declined (a Metal kernel has no device rank). Still unmeasured: the barrier-less racy-reverse control (nondeterministic, not asserted), subgroup-scope atomics (declined by name), simdgroup functions and MMA (not lowered), any width other than 32.
