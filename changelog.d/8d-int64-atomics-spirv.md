kind: SPIR-V kernels lower 64-bit integer atomics; required_features names the device features a module needs (ROADMAP 8d)
---
`vulkane-spirv-emit` lowers `AtomicRmw`/`AtomicCas` in `I64`/`U64` kernels to the 64-bit `OpAtomic*` instructions (signed or unsigned min/max by the dtype) and declares `Int64Atomics` once, only for a kernel that has one. New `vulkane_spirv_emit::required_features(words) -> RequiredFeatures { shader_int64, int64_atomics }` reads a generated module's capabilities: **enabling `shaderInt64` (and `shaderBufferInt64Atomics` or `shaderSharedInt64Atomics`) at device creation is the host's job**, the emitter cannot see the device, and on the harness GPU a device created without `shaderInt64` ran an `Int64` module with no error, so the driver is no guard (a test reports this). The kernel `Cast` added for 64-bit kernels is **wrapping only**: an integer cast to the compute dtype, never a saturating cast; float and clamping casts still decline. Tests: 1024 contended 64-bit adds, a signed max and a compare-exchange exact past 2^32 on a device (a plain 64-bit add reached 1 of 1024), the capability declared once and only with an atomic, signed/unsigned instruction choice, spirv-val. Float atomics and GLSL/HLSL/WGSL 64-bit atomics remain todo.
